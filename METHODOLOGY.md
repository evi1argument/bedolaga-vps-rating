# Методика

Документ описывает, как из выгрузки Telegram получается рейтинг. Любую цифру в README можно воспроизвести, запустив `python scripts/build.py` на тех же исходниках.

---

## Данные

| | |
|---|---|
| Источник | Telegram-чат «Тесты VPS», экспорт в JSON через Telegram Desktop |
| Что лежит в репозитории | `data/raw/*.json` — выгрузки без изменений |
| Что считается тестом | сообщение со скриншотом, узнанным брендом и текстом от 60 символов (без скриншота — от 150) |
| Период текущего датасета | указан в шапке README и в `rating.json` |

Выгрузки не редактируются. Всё, что нужно поправить руками, живёт в `data/overrides.json` и ссылается на `msg_id`.

---

## Шаг 1. Разбор — `scripts/parse_export.py`

Выход: `data/processed/tests.csv`, одна строка на тест.

**Определение бренда.** По словарю `data/brands.json` (137 брендов, ~360 алиасов). Побеждает алиас, встретившийся в тексте **раньше** остальных: тест почти всегда начинается с названия хостинга, а дальше по тексту легко всплывает чужой бренд. Строка «Beget … использую как мост к Hetzner» — это тест Beget, а не Hetzner.

Что не распозналось — уходит в `data/processed/unmatched.csv` целиком, а не молча теряется. Сейчас там ~5%: это реплики в треде и апдейты к чужим тестам.

**Флаги теста:**

| Флаг | Как ставится |
|---|---|
| `has_referral` | регулярка по `реф`, `ref_id=`, `?ref=`, `/aff` |
| `vendor_post` | самораскрытие вида «я представитель», «мы в X затестили», «у нас открылся» |
| `verdict` | вердикт **автора** теста: `positive` / `negative` / `neutral` / `satire` / `unknown` |
| `verdict_source` | `override` (размечено руками) или `heuristic` |

## Шаг 2. Оценка — `scripts/score.py`

### Классификация реакций

Три списка в `data/reactions.json`: `positive`, `negative`, `ambiguous`. Требование жёсткое: **каждая реакция, встреченная в дампе, обязана попасть ровно в один список**, иначе `validate.py` падает.

Это исправляет главную дыру прежней методики: 😁 и 🤣 — 3-я и 7-я по массовости реакции в чате — не входили ни в один список, и около четверти всего отклика просто не считалось.

`ambiguous` (😁 🤣 🤔 и подобные) в Score не идут, но выводятся отдельным числом. Они не несут знака: одинаково часто означают «смешно, потому что хорошо» и «смешно, потому что позор».

**Кастом-эмодзи.** Telegram-экспорт отдаёт их без `document_id` — опознать нечем. Считаются отдельной колонкой и в Score не идут. В текущем датасете их ~200; самый заметный случай — тест Play2Go, где автор устроил голосование ✔️/❌ кастомными эмодзи, и все 39 голосов нечитаемы.

### Правило разгромного обзора

Ключевое отличие от старой методики.

Под разгромным обзором ❤ и 🔥 означают **«согласен с критикой»**, а не «хороший хостинг». Поэтому при `verdict = negative` весь отклик — и плюсы, и минусы — засчитывается в минус.

Живой пример: обзор AdminVPS от 05.09.2026 («по праву самый отвратительный хостинг… кромешный ад за 30 дней») собрал 🔥×22. По старой формуле это дало бы бренду **+26**. По новой — это −26, потому что 22 человека согласились с разоблачением.

Обратное правило тоже работает: на **положительном** обзоре знак реакций не переворачивается. Тест 4VPS («взял на тест, пока норм, отвалов не было») собрал 💩×8 — это недоверие аудитории к выводу автора, и оно честно идёт в минус.

Переворот знака — сильная операция, она способна превратить 🔥×22 в минус. Поэтому она срабатывает **только по подтверждённой вручную разметке** из `overrides.json`. Негативный вердикт от эвристики считается обычным образом и попадает в `data/processed/review.csv` — очередь на проверку.

### Что не считается вовсе

- **Сатира.** Пародийные обзоры («пиринги с Марсом, 23000 мс») исключены. Раньше такой пост Play2Go записали в рост Score.
- **Посты представителей хостинга.** Реклама — не тест. Реакция аудитории на них сохраняется отдельными полями `vendor_pos` / `vendor_neg`.

### Ранжирование

Основной ключ — **нижняя граница 95% доверительного интервала Уилсона** для доли положительных реакций:

```
         p̂ + z²/2n − z·√( (p̂(1−p̂) + z²/4n) / n )
score =  ─────────────────────────────────────────
                      1 + z²/n
```

где `p̂` — доля плюсов, `n` — всего голосов, `z = 1.96`.

Зачем не сумма «плюсы минус минусы»: сумма поощряет количество тестов, а не качество хостинга. Бренд с 33 тестами набирает больше просто потому, что его чаще тестируют. Уилсон отвечает на правильный вопрос — «какова доля одобрения в худшем правдоподобном случае» — и автоматически занижает оценку там, где голосов мало. Подробный разбор: [Evan Miller, How Not To Sort By Average Rating](https://www.evanmiller.org/how-not-to-sort-by-average-rating.html).

В README рядом с полоской показана и фактическая доля плюсов: полоска — нижняя граница, процент — наблюдаемое значение.

### Достоверность выборки

| Значок | Голосов |
|---|---|
| ●●● | 25+ |
| ●●○ | 10–24 |
| ●○○ | 1–9 |
| — | реакций нет |

Бренды с менее чем 5 голосами выносятся в раздел «Мало данных». Это не оценка: по ним нечего считать, и ставить их в общий список было бы враньём. Отдельно считается `silent_tests` — тесты, на которые вообще не отреагировали. Молчание аудитории ≠ нейтральная оценка.

### Тренд

Отдельно считается Score за последние 90 дней. 📈 / 📉 в README — расхождение свежего окна с общей картиной больше чем на 0.08.

## Шаг 3. Рендер — `scripts/render.py`

README собирается из `rating.json` и `content/*.md`. **Руками README не правится** — правки перетрутся при следующей сборке.

- `content/guide.md` — «что взять под задачу», редакторский текст
- `content/warnings.md` — предупреждения о рисках

Границы категорий (0.55 / 0.30 / 0.15) подобраны по фактическому распределению, а не назначены заранее.

## Шаг 4. Проверка — `scripts/validate.py`

Возвращает ненулевой код, если что-то не сходится. `build.py` на этом останавливается: лучше не выпустить обновление, чем выпустить его с расходящимися цифрами.

Что проверяется:

1. Все реакции из дампа классифицированы
2. Эмодзи не стоит в двух списках сразу
3. Алиасы брендов не пересекаются и не слишком короткие
4. Каждый бренд из `tests.csv` есть в `brands.json`
5. `raw = pos − neg`, `votes = pos + neg`, `tests = scored + satire + vendor`
6. Wilson в пределах [0, 1]
7. Ранжирование монотонно
8. README отрендерен из текущего `rating.json` и даты совпадают
9. Каждый override несёт объяснение в поле `note`
10. Предупреждения ссылаются на бренды, которые есть в рейтинге
11. Данные не старше 45 дней

## Обновление рейтинга

```bash
# 1. Выгрузить чат «Тесты VPS» через Telegram Desktop в JSON
cp result.json data/raw/tests_YYYY-MM-DD.json

# 2. Пересобрать
python scripts/build.py

# 3. Разобрать очередь
#    data/processed/unmatched.csv — бренд не определён, дополнить brands.json
#    data/processed/review.csv    — спорные вердикты, разметить в overrides.json

# 4. Пересобрать ещё раз и закоммитить
python scripts/build.py
```

Старые выгрузки из `data/raw/` не удаляются: скрипт читает все файлы и дедуплицирует по `msg_id`, так что история накапливается.

## Чего методика не умеет

Честный список ограничений.

- **История до 13.05.2026 недоступна.** Выгрузки, с которых построен текущий датасет, начинаются с этой даты. Оценки из прежних версий README (январь–май 2026) считались вручную по другой методике и в текущие цифры не входят. Сравнивать старый Score и новое «Одобрение» напрямую нельзя.
- **Вердикт автора определяется эвристикой**, если тест не размечен руками. Эвристика ошибается — поэтому переворот знака требует подтверждения, а спорные случаи выписываются в `review.csv`.
- **Кастом-эмодзи не опознаются** — ограничение формата экспорта Telegram, а не методики.
- **Один тест — один бренд.** Сравнительные посты про несколько хостингов приписываются первому упомянутому.
- **Реакция ≠ проверка.** Это измерение мнения чата, а не независимое тестирование. Люди реагируют и на текст, и на автора, и на мем.
